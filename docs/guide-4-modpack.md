# 自托管 AI 伙伴 · 第四阶段手册：换个世界还能玩（整合包）

草稿 · 2026-10-23 · 接第三阶段（docs/guide-3-guide.md）之后

前三本把伙伴从帮手做到向导，但它的全部常识都是**原版**的：哪些方块能挖、怎么合成、通关走哪条路。换一个有上百个模组的整合包，这些常识一半过时、一半缺失。这本手册的目标是：**进一个新整合包，它能在没人教的情况下看懂新物品和新配方，按整合包自己的任务线带你走。**

这本是三本续篇里最"远"的，很多细节要等真的选定一个整合包才知道。所以它的结构是：先说清前三阶段必须守住什么才换得动，再给一条换法，任务单只定边界。

## 读之前：为什么前三阶段的做法决定了这一步难不难

回头看三层：

| 层 | 原版时的做法 | 换整合包时 |
| --- | --- | --- |
| 执行 | 动作写在模组里，动作本身不认具体方块（"挖白名单里的方块""按配方合成"） | **几乎不用改**：挖、合成、放置、走路对任何方块都一样 |
| 决策 | 拆步骤、失败处理、空闲提议，输入是"阶段 + 缺什么 + 事实" | **不用改**：换的是输入里的内容 |
| 知识 | `knowledge/` 的几份文件 + 从游戏读配方 | **全部换**：白名单、通关地图、计划示例都要重来；配方本来就从游戏读，自动跟上 |

所以第四阶段的工作量取决于一件事：**前三阶段有没有把游戏常识全放进知识层、没往代码里漏**。做前三本时每遇到一个"这个常识写在哪"的问题，答案都应该是"写进 knowledge/"。这本手册的第 0 步就是检查这一点。

**铁规矩再加两条**：

7. **新物品不认识就不碰**：知识层里没有的方块和物品，不挖、不放、不用，只能捡和交付。认识一样再放开一样。
8. **机器和能量设备只看不碰**：整合包里的机器、管道、线缆、储罐一律当成"建筑"，除非某张任务单明确放开某一种。

## 做完的标准

| 编号 | 你能做到的事 | 怎么算通过 |
| --- | --- | --- |
| A | 新整合包第一次进服 | 它能说出自己认识多少物品、不认识多少，不会因为不认识而报错或乱动 |
| B | "这个东西是什么、怎么做"（指一个模组物品） | 它从游戏数据里查到名字和配方，用中文说明，配方里的材料也能递归说清 |
| C | 整合包任务书（FTB Quests 等）的当前任务 | 它读得到当前任务要什么，能把它变成一个计划（第二阶段的 Plan） |
| D | "带我做完这一章" | 按任务书顺序一个一个提议和执行，你决定每一步 |
| E | 换第二个整合包 | 只改知识层和一份整合包描述文件，代码不改或只改适配器 |
| F | 前三阶段标准 | 在原版服务器上仍全部通过（知识层能按服务器切换） |

## 第 0 步 · 检查前三阶段的"漏网之鱼"

```text
任务单 24 · 常识审计
1. 在 mod/ 和 server/ 的代码里搜所有 "minecraft:" 字面量和物品/方块名；每一处要么挪进 knowledge/，要么证明它是协议或测试里的例子。
2. 列出所有"原版才成立"的假设：维度名、床的判定、食物判定、时间值（12542 等）、敌对生物判定；每一条标注在整合包里可能怎样变。
3. 让 knowledge/ 支持"按服务器选一套"：config.yaml 加 knowledge_set: "vanilla"，目录变成 knowledge/vanilla/、knowledge/<整合包名>/。
验收：审计表格入库 docs/；原版服务器回归全过。
```

## 第 1 步 · 让它从游戏里学物品和配方

### 1.1 任务单 25 · 物品字典（导出 + 中文名）

```text
任务：
1. 模组加一个开发命令（只在客户端、只对主人有效）：导出当前加载的全部物品 id、显示名（当前语言）、所属模组、标签（tags）到 knowledge/<包名>/items.json。
   显示名直接用游戏的本地化结果，所以整合包装了中文语言包就是中文，没装就是英文，不再维护 items_zh.json。
2. 后台的 ItemNames 改为优先读这份导出，原版的 items_zh.json 作为兜底。
3. 白名单改为"按标签"：mineable 用 tags（minecraft:logs、forge:ores/* 等）而不是列 id，这样新模组加的矿和木头自动进名单；never_touch 同样按标签 + 按模组前缀（例如所有 mekanism: 的方块）。
验收：A、B 的"是什么"。
```

### 1.2 任务单 26 · 配方递归与"怎么做"

```text
任务：
1. craft 的配方查询已经走客户端 RecipeManager，扩展到模组的配方类型：至少支持 shaped / shapeless / smelting / 整合包最常见的 1–2 种机器配方（只用于"解释"，不用于执行）。
2. 新工具 explain_recipe(item)：递归展开到原材料（深度 ≤ 4），返回一棵树；Brain 用它回答"怎么做"，并能把"做 X"拆成 Plan（只到伙伴会做的工序为止，机器工序交给主人并说清）。
3. 没有配方或只能用机器做的 → 明确说"这个要用 XX 机器，我只能帮你准备材料"。
验收：B 全部；10 个随机模组物品的解释和游戏内 JEI 对照一致。
```

## 第 2 步 · 任务书就是通关地图

```text
任务单 27 · 任务线适配器
1. 目标：第三阶段的 progression.yaml 对整合包来说由任务书代替。做一个适配器接口 QuestSource：当前章节、当前可做任务、任务要求（物品/数量/行为）、完成状态。
2. 第一个实现：FTB Quests（最常见）。读法待定：优先客户端读任务数据（模组侧有 API），其次读存档文件；两条路都写一份调研结论再选。
3. 没有任务书的整合包：允许手写一份 progression.yaml 放进 knowledge/<包名>/，格式同第三阶段。
4. 空闲提议的输入换成 QuestSource 的输出；report_progress 答"当前章节 + 当前任务 + 缺什么"。
验收：C、D。
```

## 第 3 步 · 整合包描述文件和切换

```text
任务单 28 · 一包一份 pack.yaml
1. knowledge/<包名>/pack.yaml：包名、MC 版本、Forge/NeoForge 版本、任务书类型、危险维度列表、特殊规则（例如"这个包里木头不能用手撸"）。
2. 服务器与客户端：mini 上第二个 mcserver 目录（不同端口）、Prism 第二个实例；keeper.yaml 和 config.yaml 支持按"当前包"切换（一份配置一个包，launchd 服务名带包名）。
3. 第一本手册的 2.x、3.x 对第二套服务器/实例重做一遍（整合包的服务端安装方式不同，这一段到时按包补细则）。
验收：E、F。
```

## 第 4 步 · 验收

| 场景 | 通过 |
| --- | --- |
| 进新包第一分钟 | 它报告认识/不认识的比例，无报错，无乱动 |
| 指 10 个模组物品问"是什么、怎么做" | 10 次正确 |
| 任务书第一章 | 它提议、你决定，做完一章 |
| 切回原版服务器 | 前三阶段全部标准通过 |

记到小本子：导出物品数量、不认识的比例、任务书读取用的哪条路、切换一次包要改哪些文件。

## 术语

- **知识集（knowledge set）**：一套游戏常识文件，一个服务器用一套；原版是 `knowledge/vanilla/`。
- **任务书**：整合包自带的引导任务系统（FTB Quests、Better Questing 等），在这一阶段充当"通关地图"。
- **适配器**：把不同任务书读成同一种格式的那层代码；换任务书只换它。
